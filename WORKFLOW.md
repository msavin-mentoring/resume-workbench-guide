# Сборка и проверка резюме

Этот гид — короткая рабочая последовательность; подробные правила находятся в локальном скилле `msavin-resume`. На выходе для **каждого** ученика четыре файла: `resume.md`, `claim-ledger.md`, `interview-legend.md`, `vacancy-coverage.md`.

## 1. Собрать источники и границы

В `claim-ledger.md` записать: собственное резюме ученика, разговоры, проекты/репозитории, даты и роль, продукт и команда, вакансии, публичные сведения. Для каждого источника указать, что именно он доказывает. Локальный чужой SQLite-корпус `local/resume-context.sqlite` применять только для поиска знакомых инженерных задач и структуры формулировок; он не подтверждает технологии, метрики, место работы или личный вклад ученика. Донорский сценарий включать только при явном списке разрешённых доноров для этого ученика.

Готово, когда понятны реальный работодатель/проект, зрелость продукта, границы роли и источники каждого предлагаемого достижения.

## 2. Разобрать проекты до написания достижений

Для каждого проекта установить: что делает продукт, существовало ли решение до прихода ученика, какие подсистемы он менял, стек, команда, интеграции, ограничения и известный масштаб. В спорных местах сформулировать узкий вопрос ученику, а не переносить к нему достижения других людей.

Готово, когда сильные глаголы (`разработал`, `спроектировал`, `оптимизировал`) имеют правдоподобную границу личной ответственности.

## 3. Проверить каждый candidate claim

В `claim-ledger.md` каждому пункту дать ID и заполнить короткий аудит:

1. **Факт:** ученик действительно делал это, только рассказал, это обоснованная реконструкция или чужой пример?
2. **Сила:** есть проблема/ограничение → его действие и механизм → наблюдаемый результат? Если только технология или обычная задача — перенести в обязанности.
3. **Конкретность:** есть подтверждённый масштаб/число/сравнение? Если число в `[квадратных скобках]`, указать, что это рабочая подстановка, и способ замера: baseline, результат, период, область, источник.
4. **Рынок:** какому требованию `V-...` отвечает пункт? Отсутствие требования не делает сильное достижение бесполезным; частотное требование не делает неподтверждённый факт правдой.
5. **Решение:** в достижения / в типовые задачи / в резерв / исключить. Указать, что проверить и что кандидат должен объяснить на интервью.

Готово, когда каждый пункт резюме трассируется к ID и ни один чужой пример не выдан за факт ученика.

## 4. Сопоставить с вакансиями

Для PHP backend сначала отфильтровать подходящие карточки в [датированной выборке](references/vacancy-sample-2026-09-29.md), затем использовать [локальный построчный банк](references/vacancy-bank-2026-09-29.md): `T` — задачи, `R` — обязательные требования, `P` — плюсы, `S` — стек/контекст. Не обращаться к сайтам на каждом проходе coverage; первоисточник нужен для спорного пункта или проверки текущего статуса. Короткие точные словосочетания для формулировок — в [языке вакансий](references/vacancy-language-2026-09-29.md).

Сгруппировать эквивалентные `T`/`R` по смыслу; разделить специфичные для фреймворка и переносимые backend-навыки. В coverage перечислить ID исходных пунктов, посчитать частоту по **разным вакансиям** и указать `explicit`, `semantic`, `missing` или `conflicting` и решение `retain`, `strengthen`, `discuss`, `omit`. `P` держать отдельно от обязательного, а `S` не считать требованием автоматически. По старому raw-списку **не** считать частоту «вакансий»: там нет границ и ID.

Готово, когда важные пробелы имеют либо подтверждающее достижение, либо вопрос ученику, либо причину сознательно не включать требование.

## 5. Выпустить и провалидировать пакет

В `resume.md` для каждой позиции держать порядок «проект → стек → достижения → типовые задачи → команда», если секция применима. В стек включать технологии, а не названия провайдеров и общие действия. В `interview-legend.md` на каждый сильный пункт записать исходную проблему, механизм, компромиссы, проверку результата, личную границу и вопросы интервьюера.

Перед отправкой работодателю проверить: даты и факты, все `[плейсхолдеры]`, метрики, противоречия между четырьмя файлами, отсутствие чужих данных и то, что ученик может объяснить каждое утверждение. Рабочий черновик допускает подстановки; финальная версия — только согласованные формулировки.

Готово, когда публичное резюме понятно само по себе, а ledger и легенда позволяют защитить каждое существенное утверждение.
